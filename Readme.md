# SocketCAN: Software-Only CAN/CAN FD Communication on Linux

## Overview

This project explores **SocketCAN**, the Linux framework for Controller Area Network (CAN) communication, and demonstrates CAN and CAN FD communication without requiring physical CAN hardware.

A **Virtual CAN (`vcan`) interface** is used to create a software-only CAN network. Multiple software-based Electronic Control Units (ECUs) are implemented in C and communicate through the virtual CAN interface.

The project demonstrates CAN message transmission, reception, filtering, logging, node failure detection, basic diagnostics, transmission-rate analysis, and CAN FD communication.

---

## Objectives

* Understand the Linux SocketCAN framework.
* Create a software-only CAN network using Virtual CAN.
* Develop multiple CAN communication nodes using C.
* Implement CAN message transmission and reception.
* Implement CAN message filtering.
* Log CAN traffic into a CSV file.
* Detect unknown CAN messages.
* Analyze CAN transmission rates.
* Demonstrate node failure detection.
* Implement basic diagnostic warning mechanisms.
* Explore CAN FD communication and larger payloads.

## CAN Message Definitions

The project uses CAN identifiers to represent different vehicle parameters.

| CAN ID  | Signal              | Payload | Unit |
| ------- | ------------------- | ------: | ---- |
| `0x100` | Vehicle Speed       | 2 bytes | km/h |
| `0x101` | Engine RPM          | 2 bytes | rpm  |
| `0x102` | Coolant Temperature |  1 byte | °C   |

These messages are generated by the Vehicle ECU and received by the Dashboard ECU and Logger ECU.

## Source Code

The `Source_Code` directory contains the following applications:

### `vehicle_ecu.c`

Acts as the vehicle-side CAN transmitter.

It generates vehicle parameters such as:

* Vehicle speed
* Engine RPM
* Coolant temperature

and periodically transmits them over the Virtual CAN interface.

### `dashboard_ecu.c`

Acts as the Dashboard ECU.

It:

* Receives CAN frames.
* Decodes vehicle parameters.
* Displays the received values.
* Uses CAN filters to process only relevant messages.

### `logger_ecu.c`

Acts as the CAN traffic logger.

It:

* Receives CAN traffic.
* Records CAN messages.
* Stores decoded information in a CSV log.
* Helps analyze communication activity.

### `canfd_sender.c`

Transmits CAN FD frames containing larger payloads than classical CAN.

### `canfd_receiver.c`

Receives and displays CAN FD frames transmitted by the CAN FD sender.

## Virtual CAN Setup

The project uses a Linux Virtual CAN interface instead of physical CAN hardware.

Example setup:

```bash
sudo modprobe vcan
sudo ip link add dev vcan0 type vcan
sudo ip link set up vcan0
```

The interface can be inspected using:

```bash
ip -details link show vcan0
```

---

## CAN Communication Testing

CAN traffic can be monitored using:

```bash
candump vcan0
```

A test CAN frame can be transmitted using:

```bash
cansend vcan0 100#1234
```

The transmitted frame can then be observed using `candump` or the developed ECU applications.

---

## CAN Message Filtering

SocketCAN filtering is used to allow an application to receive only selected CAN identifiers.

For example, the Dashboard ECU can filter specific vehicle messages such as:

```text
0x100 → Vehicle Speed
0x101 → Engine RPM
0x102 → Coolant Temperature
```

This demonstrates how CAN applications can process only the messages relevant to them.

---

## CAN Traffic Logging

The Logger ECU records CAN communication into a CSV file.

The log can contain information such as:

```text
Timestamp, CAN ID, DLC, Data
```

This allows CAN traffic to be inspected and analyzed after the communication experiment.

## Experiments Performed

The following experiments were performed during the project:

### 1. Virtual CAN Interface

Created and verified the `vcan0` interface for software-only CAN communication.

### 2. Vehicle ECU Transmission

The Vehicle ECU transmitted vehicle parameters through the virtual CAN network.

### 3. CAN Traffic Observation

CAN traffic was simultaneously observed by multiple software applications, including the Dashboard ECU, Logger ECU, and `candump`.

### 4. Dashboard Reception

The Dashboard ECU received and decoded vehicle parameters from CAN frames.

### 5. CAN Traffic Logging

The Logger ECU recorded CAN traffic into a CSV file.

### 6. CAN Message Filtering

CAN filters were implemented to process selected CAN identifiers such as speed and RPM messages.

### 7. Unknown Message Detection

Unknown CAN identifiers were transmitted and detected by the logging/monitoring application.

### 8. Transmission Rate Experiment

CAN transmission was tested with a periodic transmission interval of approximately **100 ms** to observe communication behavior.

### 9. Node Failure Detection

Node activity was monitored to identify the absence of expected CAN communication.

### 10. Diagnostic Warning

A basic diagnostic warning mechanism was demonstrated when expected communication was unavailable.

### 11. CAN FD Communication

CAN FD communication was demonstrated using a Virtual CAN FD interface and larger payloads.

A CAN FD frame containing a payload larger than the classical CAN maximum of 8 bytes was successfully tested.

## CAN FD Demonstration

The project also investigates **CAN FD (Flexible Data-rate)** communication.

The CAN FD experiment demonstrates:

* CAN FD frame transmission.
* CAN FD frame reception.
* Larger payload sizes.
* Software-only CAN FD communication.
* Use of a Virtual CAN FD interface.

Example observed payload:

```text
11 22 33 44 55 66 77 88 99 AA BB CC DD EE FF 00
```

This demonstrates a **16-byte CAN FD payload**.
